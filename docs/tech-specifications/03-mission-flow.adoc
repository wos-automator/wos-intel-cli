== Mission Flow (`wos_intel/flow.py`, `wos_intel/state.py`)

[#TS-3.1]
=== TS-3.1 Runner and run loop

Implements <<FR-3.1>>, <<FR-3.2>>, <<FR-3.3>>, <<FR-3.7>>, <<FR-3.8>> and <<FR-4.3>>.

[source,python]
----
class Device(Protocol):          # implemented by adb.Adb and by the fake game of the tests
    def check(self) -> None: ...
    def screenshot(self) -> Image: ...
    def tap(self, x: int, y: int) -> None: ...
    def back(self) -> None: ...

Runner(config, device, detector, store, *, dry_run=False, debug_dir=None,
       sleep=time.sleep, clock=time.monotonic, now=datetime.now)
Runner.run() -> Outcome
----

`Outcome`: `NOTHING_TO_DO`, `OUT_OF_STAMINA`, `NO_TROOPS`, `MISSION_LIMIT`, `DRY_RUN` (regular,
`ok`), `WRONG_SCREEN`, `TOO_MANY_FAILURES` (not `ok`).

[plantuml]
----
@startuml
start
:device.check();
:observe;
if (WORLD / INTEL*?) then (no)
  :WRONG_SCREEN;
  stop
endif
repeat
  if (missions >= max_missions?) then (yes)
    :MISSION_LIMIT;
    stop
  endif
  :enter Intel (tap Intel button on WORLD);
  :read stamina;
  if (INTEL_CLAIMABLE?) then (yes)
    :Claim All -> REWARDS -> tap 360,180 -> INTEL;
  else (no)
    :detect symbols, build candidates;
    if (stamina < 10 / none / none affordable?) then (yes)
      :OUT_OF_STAMINA or NOTHING_TO_DO;
      stop
    endif
    :choose target (TS-3.3);
    :run mission (TS-3.2);
  endif
repeat while (continue)
@enduml
----

The diagram omits two refinements. Boss last (<<FR-3.3>>): `choose_target` receives the
affordable candidates without the boss; only if that list is empty does it receive the boss.
Settling (<<FR-3.7>>): every regular end (`NOTHING_TO_DO`, `OUT_OF_STAMINA`, `MISSION_LIMIT`)
goes through `Runner._settle(final, symbols)`. It returns `final` at once if no symbol is
`RUNNING` and `_unclaimed` (missions started since the last claim) is 0. Otherwise it polls
every `timing.completion_poll` (10 s) for up to `timing.completion_timeout` (900 s):
`INTEL_CLAIMABLE` → `_claim` (resets `_unclaimed`) and `None`, so the loop evaluates the Intel
screen again; `INTEL` → keep waiting; any other state → `StepFailed`. On timeout it logs a
warning and returns `final`. `_unclaimed` exists because a greyed-out running pin is not always
found by the white mask (SPEC.md §3.5).

Expert (<<FR-3.8>>): on every evaluation of the Intel screen `Detector.find_expert` is asked
for the sign and a hit is logged (`expert sign at x,y`), so a dry run always shows it. It is
tapped after the mission-limit check and before the stamina check, if every candidate is a
boss (or there is none) and `_expert_used` is not set. The sign (template `expert_sign`, cut by `tools/cut_templates.py` from the inside
of the sign in `ref/intel-expert-available.png`, region `regions.expert_sign`; other references
score ≤ 0.57). If found: set `_expert_used`, tap the match, return `None` so that the loop
evaluates the Intel screen again. What the game shows after the tap has no reference yet; a
screen other than `INTEL*` runs into the normal `StepFailed` recovery (<<TS-3.5>>).

Candidates are the `AVAILABLE` symbols that were not attempted in this run (same type within
`lock_radius` of an attempted one) and, for the boss, not locked (<<TS-3.4>>). With `dry_run`
the runner logs the tap it would send (Intel button, Claim All, first mission) and returns
`DRY_RUN` without calling `tap` or `back`.

[#TS-3.2]
=== TS-3.2 Mission sequences

Implements <<FR-3.4>>.

[plantuml]
----
@startuml
[*] --> MISSION_DIALOG : tap symbol
MISSION_DIALOG --> WORLD_TARGET : type ok, tap View
MISSION_DIALOG --> [*] : type mismatch (rejected)
WORLD_TARGET --> SQUAD : COMBAT, tap Explore
WORLD_TARGET --> DEPLOY : HUNT/BOSS, tap Attack
WORLD_TARGET --> WORLD : RESCUE, tap Rescue
WORLD_TARGET --> [*] : wrong action (rejected)
SQUAD --> RESULT : tap Fight, up to 60 s
RESULT --> WORLD : tap exit text
DEPLOY --> WORLD : prevail hint or BOSS, tap Deploy
DEPLOY --> [*] : HUNT without prevail hint (rejected)
WORLD --> INTEL : tap Intel button
@enduml
----

Control flow uses three exceptions, handled in `Runner.run`:

[cols="1,3"]
|===
|Exception |Meaning and handling

|`MissionRejected` |Plausibility or safety check failed. Recovery (<<TS-3.5>>), next symbol; not counted as a failure.
|`StepFailed` |Expected state did not appear. Counted; recovery; after `max_failures` in a row `TOO_MANY_FAILURES`.
|`RunEnded(outcome)` |`NO_STAMINA` or `NO_TROOPS` dialog: one BACK, the run ends with that outcome.
|===

Dialog type under a banner: if `dialog_type` returns `None` on the first `MISSION_DIALOG`
screenshot, `_run_mission` polls (`poll_interval`, up to `expect_timeout`) and asks again on
each fresh screenshot; a state other than `MISSION_DIALOG` raises `StepFailed`. A positively
recognised other type rejects at once. Found on the device run of 2026-10-10: two dialogs
opened under a notification banner (`ref/hunt-1-dialog-banner.png`,
`ref/rescue-1-dialog-banner.png`), were rejected immediately and their missions were then
passed over in favour of the boss.

`ACTION_FOR` maps COMBAT → EXPLORE, HUNT/BOSS → ATTACK, RESCUE → RESCUE. The target is added
to the attempted list before the first tap, so no symbol is tapped twice in a run.

[#TS-3.3]
=== TS-3.3 Target selection with overlap

Implements <<FR-3.3>>.

* `mission_cost(config, type)` returns the cost from `[costs]`.
* `find_occluder(config, target, symbols)`: a symbol closer than `overlap_distance` (30 px)
  whose ground ring is lower on the screen; ring y = centre y + `ring_offset_pin` (55) or
  `ring_offset_boss` (65).
* `choose_target(config, candidates, symbols) -> (Symbol, Point)`: starts with the first
  candidate. If it has an occluder that is itself a candidate, the occluder becomes the target
  (repeated). If the occluder is not a candidate, the tap point is
  `centre + edge_tap_radius (20) × unit(centre − occluder)`, i.e. on the disc edge opposite to
  it.

[#TS-3.4]
=== TS-3.4 Boss lock (`wos_intel/state.py`)

Implements <<FR-3.5>>.

[source,json]
----
{ "boss": { "attacked_at": "2026-10-09T19:00:00", "locked_until": "2026-10-10T01:59:27" } }
----

`StateStore(path)`: `boss_locked(now)`, `boss_locked_until()`, `lock_boss(now, cycle_seconds)`.
Writing goes to `state.json.tmp` followed by `os.replace`. A missing, unreadable or malformed
file means "not locked". The runner reads the refresh timer from the Intel screenshot on which
the boss was selected and locks after the march has started; an unreadable timer falls back to
`boss.fallback_cycle_hours`.

[#TS-3.5]
=== TS-3.5 Waiting and recovery

Implements <<FR-3.6>>.

* `_tap` / `_back`: log, send, `sleep(tap_delay)`.
* `_observe`: fresh screenshot → `detect_state`; logs the state; writes
  `debug/<step>-<STATE>.png` when debugging.
* `_expect(states, timeout=expect_timeout)`: observe; return on a wanted state; raise
  `StepFailed` once the deadline has passed; otherwise `sleep(poll_interval)` and repeat.
* `_recover`: up to `max_back` times: observe; stop on `INTEL*` or `WORLD`; `REWARDS` → tap the
  rewards exit; `VICTORY`/`DEFEAT` → tap the exit text; anything else → BACK.

* `_save_failure`: on `MissionRejected` and `StepFailed` the last observed screenshot is written
  unannotated to `debug/failure-<step>-<STATE>.png` (`failure_dir`, always set by the CLI), so
  that an unknown dialog can be turned into a reference.

`sleep`, `clock` and `now` are injected, so the tests run without real waiting.
