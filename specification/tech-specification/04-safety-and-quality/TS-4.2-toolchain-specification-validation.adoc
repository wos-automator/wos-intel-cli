[[TS-4.2]]
=== TS-4.2 Toolchain and specification validation

Implements <<NFR-1>> and <<NFR-2>>.

* Python ≥ 3.11, dependencies and tasks in `pyproject.toml`, environment managed with `uv`
  (`uv sync`). Runtime: `numpy`, `opencv-python`. Development: `pytest`, `pytest-mock`,
  `pytest-bdd`, `ruff`, `mypy`, `poethepoet`.
* `uv run poe check` = `ruff check .` + `ruff format --check .` + `mypy` (strict) + `pytest` +
  `.agents/skills/spec-system/bin/validate-specs`. Ruff rule `T20` forbids `print`. `pytest` there
  deselects the acceptance scenarios; `uv run poe bdt` runs them and writes Cucumber JSON to
  `build/bdt/cucumber.json`.
* pytest markers map the test pyramid: `unit` (pure logic and detection on reference
  screenshots), `component` (one module with fakes/mocks: flow with a scripted fake game, ADB
  with a mocked `subprocess.run`), `integration` (configuration and state files, CLI
  in-process), `bdt` (the acceptance scenarios of `specification/acceptance/`, run by
  `pytest-bdd` from `tests/bdt/`: the CLI as a separate process on reference screenshots).
  The run-loop tests use `CachingDetector` (`tests/conftest.py`): the fake game shows the same
  screenshots again and again, so each one is detected once per test module, keyed by its
  content. The detection itself is tested uncached in `tests/test_detect.py`.
* Specification layout: each master includes `specification/<kind>/<NN-chapter>/index.adoc`;
  the chapter index includes one file per item (`<ID>-<slug>.adoc`), resolved relative to the
  index. Release notes are one file per version in `specification/release-notes/`.
* Specification validation: spec-validator, run by the launcher of the agent-skills library
  (`.agents/skills/`, vendored with its `vendor.sh`), which runs the release pinned in
  `.agents/spec-validator.lock` and verifies its checksum. It checks that masters and `include::` targets exist, nested includes
  are followed relative to the including file; every file below the master's folder is reached
  by an include; anchors `+[[FR-x.y]]+`, `+[[NFR-x]]+`, `+[[TS-x.y]]+`, `+[[US-x.y]]+` are unique
  and in the folder of their kind; every `+<<ID>>+` resolves; each TS references a requirement,
  each US a TS and a requirement; every scenario of `specification/acceptance/` has exactly one
  unique `@AT-x.y` and traces to existing requirements (`.spec-validator.json`). From the Cucumber
  JSON it writes the test report and the traceability report.
* `tools/prototype_detect.py` is the frozen prototype of SPEC.md and excluded from linting.
