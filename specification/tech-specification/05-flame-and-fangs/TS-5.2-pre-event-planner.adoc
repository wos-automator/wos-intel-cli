[[TS-5.2]]
=== TS-5.2 Pre-event planner

Implements <<FR-5.3>> and <<FR-5.4>>.

Pure logic in `wos_intel/event.py`:

[source,python]
----
class Group(StrEnum):  CLAIM, HOLD, IGNORE
class Phase(StrEnum):  CLAIM, HOLD

def classify(expires_in: int, countdown: int, tolerance: int) -> Group
    # expires_in < countdown - tolerance -> CLAIM; > countdown + tolerance -> IGNORE; else HOLD
----

Both values are seconds from the same moment: the countdown is converted once into
`event_start = now() + countdown` (logged), and each expiry into `now() + expires_in` when its
dialog is read, so `classify` gets `expiry - now()` and `event_start - now()`.

Configuration `[event]`: `tolerance_minutes = 10`, `expert_hours = 2.0`; regions in `[ocr]` and
`[regions]` as in <<TS-5.1>>.

State (`state.json`, <<TS-3.4>>), written atomically like the boss lock:

[source,json]
----
{ "event": { "hold_until": "2026-10-19T00:00:00" } }
----

`StateStore.holding(now) -> bool`, `StateStore.hold(until)`. A missing, malformed or past
entry means "not holding".

Runner integration (<<TS-3.1>>, <<TS-3.2>>):

[cols="1,3"]
|===
|Point |Behaviour while the event icon is shown

|`_iteration`, Intel screen |`_note_event` before the claim step: `find_event_icon`; with the icon, `read_event_countdown` – unreadable: poll for `expect_timeout`, then `RunEnded(EVENT_UNREADABLE)`. `_phase()`: `None` without an event start or once it has passed, `HOLD` if `store.holding(now)`, else `CLAIM`; logged when it changes.
|Claim All |`INTEL_CLAIMABLE` is only claimed in phase `CLAIM`; in `HOLD` the button is ignored (logged).
|Candidates |Symbols whose remembered group (`_groups`, by type and position like `_attempted`) is not the phase are left out; in `HOLD` remembered `CLAIM` missions too. The boss is never grouped.
|Phase change |`_start_holding`, after the expert check: in `CLAIM`, no candidate except the boss left and a mission remembered as `HOLD`. With a `RUNNING` symbol or `_unclaimed` missions it calls `_settle(NOTHING_TO_DO)` (<<FR-3.7>>): after a claim the Intel screen is evaluated again; on its timeout the run ends with `NOTHING_TO_DO` and does not hold. Otherwise `store.hold(event_start)` and the Intel screen is evaluated again, now in `HOLD`. Without a remembered `HOLD` mission the run continues as on a normal day.
|`_run_mission` |`_check_expiry` after the dialog type check (<<TS-2.4>>), except the boss: `read_expiry_seconds`, polled like the dialog type under a banner. Unreadable → `MissionRejected`. The group is remembered in `_groups`; group ≠ phase → `MissionDeferred` (new): `_iteration` takes the target off `_attempted`, `run()` logs `left for later`, BACK via `_recover`; no failure, no failure screenshot. `IGNORE` never equals a phase.
|`_settle` |In `HOLD` it returns at once, without waiting: `REWARDS_HELD` instead of `NOTHING_TO_DO`, any other outcome unchanged.
|Expert |`_expert_due()`: in a pre-event phase `False` while `event_start - now()` exceeds `expert_hours` (logged `expert held back: the event starts in N h`); otherwise as in <<TS-3.1>>. Its "only the boss left" check runs on the phase-filtered candidates, so missions of another group do not count as workable.
|===

New outcomes, both regular (`ok`): `REWARDS_HELD = "rewards held for the event"`,
`EVENT_UNREADABLE = "event countdown unreadable"`.

Without the event icon none of this applies; `state.json` keeps a stale `hold_until`, which
is ignored once it is in the past.
